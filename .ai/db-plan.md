## Database Plan (MVP) — High-Level Description

This document describes the MVP data model for AI Running Training Planner in prose (without SQL). Its purpose is to align business and technical terminology and ensure consistency with the PRD and architectural decisions.

### Architectural Assumptions

- User identity system: `auth.users` (Supabase Auth). There is no custom profile table in the MVP.
- All domain tables have `user_id uuid → auth.users(id) ON DELETE CASCADE`.
- Times and day boundaries use UTC. `planned_date` is a date (UTC); significant timestamps use `timestamptz` (`created_at`, `updated_at`, `completed_at`).
- Primary keys: `uuid`, generated by the DB. UUID generation (pgcrypto) is enabled.
- RLS is enabled on user tables; USING/WITH CHECK policies use `user_id = auth.uid()`.
- The `training_types` dictionary maintains the list of workout types; deactivate through `is_active` instead of deleting.
- Enumerations (stable values managed in the DB):
  - `workout_status`: planned | completed | skipped | canceled
  - `workout_rating`: too_easy | just_right | too_hard
  - `workout_origin`: manual | ai | import
  - `ai_suggestion_status`: shown | accepted | rejected | expired
  - `ai_event_kind`: regenerate (MVP)
  - `goal_type`: distance_by_date (MVP)

## Domain Entities

### 1) training_types (dictionary)

- Purpose: canonical dictionary of workout types used by the plan (workouts) and generator (ai_suggestions).
- Key attributes: `code` (PK, text code), `name` (readable name), `is_active` (active status), `created_at` (UTC).
- Rules: deleting a type is prohibited (RESTRICT) to preserve historical consistency; retire it using `is_active=false`.
- Initial data (seed): `easy`, `tempo`, `intervals`, `long_run`, `recovery`, `walk`.

### 2) workouts (plan and completion)

- Purpose: represents a workout session — its plan and optional completion metrics.
- Key plan attributes (always required):
  - `user_id`, `training_type_code` (→ `training_types.code`), `planned_date` (UTC), `position` (order within a day, ≥1, unique per `user_id+planned_date`),
  - `planned_distance_m` (100–100000), `planned_duration_s` (300–21600).
- Key completion attributes (required only for `status=completed`):
  - `distance_m` (100–100000), `duration_s` (300–21600), `avg_hr_bpm` (0–240), `completed_at` (UTC).
- Other attributes:
  - `status` (planned/completed/skipped/canceled), `rating` (too_easy/just_right/too_hard only for completed),
  - `origin` (manual/ai/import), `ai_suggestion_id` (present only when `origin='ai'`),
  - `steps_jsonb` (list of steps: warm-up, main part, cool-down — validated against a schema in the API),
  - `avg_pace_s_per_km` (derived: `duration_s / (distance_m/1000)`, null if data is missing).
- Integrity rules (enforced in the DB):
  - Completion metrics are required only for `status='completed'`; they must be empty for all other statuses.
  - `rating` is allowed only for `status='completed'`.
  - `origin ↔ ai_suggestion_id` relationship: `origin='ai'` if and only if `ai_suggestion_id` is not null.
  - Uniqueness of `user_id + planned_date + position` (allows multiple sessions on the same day, with ordering).
- Key relationships:
  - `training_type_code` → `training_types(code)` (RESTRICT),
  - `(ai_suggestion_id, user_id)` → `ai_suggestions(id, user_id)` (ensures owner consistency),
  - `user_id` → `auth.users(id)` (CASCADE on user deletion).

### 3) ai_suggestions (AI suggestions)

- Purpose: stores AI-generated workout suggestions before acceptance.
- Key attributes: `user_id`, `training_type_code` (→ dictionary), `steps_jsonb` (list of steps), `status` (shown/accepted/rejected/expired),
  `accepted_workout_id` (1–1 with `workouts`), `created_at`, `updated_at`.
- Rules:
  - Expiration after 24h is calculated in application logic relative to `created_at` (without an additional DB column).
  - Acceptance sets `status='accepted'` and references `accepted_workout_id`; type and date consistency is verified in the API.
  - Unique 1–1 mapping between an accepted suggestion and a workout (on both sides).

### 4) ai_suggestion_events (regeneration telemetry)

- Purpose: records “regenerate” actions (MVP) on AI suggestions to enforce limits.
- Key attributes: `user_id`, `ai_suggestion_id`, `kind` (always `regenerate` in the MVP), `occurred_at`, `metadata` (optional).

### 5) user_goals (user goals)

- Purpose: a simple distance goal within a time horizon.
- Key attributes: `goal_type` (MVP: `distance_by_date`), `target_distance_m` (>0), `due_date` (date), `notes` (optional).
- Rules: exactly one goal per user in the MVP (unique by `user_id`).

### 6) ai_logs (service logs)

- Purpose: logs AI interaction events and metrics for diagnostics and billing.
- Access: service-role only; RLS enabled and blocking `anon` and `authenticated`. Retention: 30 days (external job).
- Example attributes: `event`, `level`, `model`, `provider`, `latency_ms`, `input_tokens`, `output_tokens`, `cost_usd`, `payload`.

## Relationships and Cardinality

- `training_types (1) → (N) workouts` — historical consistency (RESTRICT).
- `training_types (1) → (N) ai_suggestions` — type dictionary (RESTRICT).
- `auth.users (1) → (N) workouts` — user data ownership (CASCADE on user deletion).
- `auth.users (1) → (N) ai_suggestions` — same as above.
- `auth.users (1) → (N) ai_suggestion_events` — same as above.
- `auth.users (1) → (1) user_goals` — exactly one goal in the MVP.
- `ai_suggestions (1) → (0..1) workouts` — acceptance: `accepted_workout_id` ↔ `workouts.id` (1–1, `user_id` consistency).
- `workouts (0..1) → (1) ai_suggestions` — AI origin: `(ai_suggestion_id, user_id)` ↔ `(id, user_id)`.

---

## Indexes (Goals and Rationale)

- `workouts (user_id, planned_date)` — fast retrieval of calendar entries (date ranges).
- `workouts (user_id, training_type_code, completed_at DESC)` — last 3 completed workouts of a given type.
- `workouts (user_id, completed_at DESC)` — last 3 completed workouts overall.
- Unique partial index `workouts (ai_suggestion_id) WHERE ai_suggestion_id IS NOT NULL` — 1–1 acceptance mapping.
- `ai_suggestions (user_id, status, created_at DESC)` — filtering by status and time (expiration, suggestion list).
- `ai_suggestion_events (user_id, ai_suggestion_id, occurred_at DESC)` — regeneration limit enforcement and auditing.
- `ai_logs (event, created_at DESC)` — optimizes GET /api/v1/internal/ai/logs with event filtering and date sorting.
- `ai_logs (level, created_at DESC)` — optimizes GET /api/v1/internal/ai/logs with level filtering and date sorting.
- Partial index `ai_logs (user_id) WHERE user_id IS NOT NULL` — optimizes queries filtering by user_id (skips null values).

---

## Helper Views

- `vw_last3_completed_per_type` — returns up to the last 3 rows with `status='completed'` for each user and workout type, sorted by `completed_at DESC`.
- `vw_last3_completed_overall` — returns up to the last 3 rows with `status='completed'` for each user, sorted by `completed_at DESC`.

- Both views use `security_invoker = true`, so access through them follows the `workouts` RLS policies: users see only their own data, and `anon` sees no workouts.

---

## Security Rules (RLS)

- RLS enabled for all six public tables, including `training_types` and `ai_logs`.
- Ownership policies: SELECT/INSERT/UPDATE/DELETE only when `user_id = (select auth.uid())` (USING and WITH CHECK). The subquery allows the user identifier to be calculated once per query. UPDATE retains both conditions, preventing ownership changes.
- `ai_logs` — RLS blocks `anon` and `authenticated`; technical access uses service-role, which bypasses RLS.
- Indexes `workouts (training_type_code)` and `ai_suggestions (training_type_code)` support foreign keys to the workout type dictionary. Existing ownership and unique indexes are preserved.

---

## Validation and Consistency (DB + API)

- Plan ranges: `planned_distance_m` 100–100000, `planned_duration_s` 300–21600.
- Completion ranges: `distance_m` 100–100000, `duration_s` 300–21600, `avg_hr_bpm` 0–240 (required only for `completed`).
- Conditional dependencies in the DB:
  - `status='completed'` ⇒ completion metrics and `completed_at` must be present; for other statuses, they must be empty.
  - `rating` is allowed only for `status='completed'`.
  - `origin='ai'` ⇔ `ai_suggestion_id` is non-empty.
- `steps_jsonb` receives minimal DB validation (must be an array); full schema validation occurs in the API.
- `avg_pace_s_per_km` is derived (may be a generated DB column; null when data is missing).

---

## Scheduled Jobs (pg_cron)

- Goal: automatically expire outdated AI suggestions every hour.
- Expiration rule: an `ai_suggestions` record with `status='shown'` and `created_at <= now() - interval '24 hours'` is marked `status='expired'`, and `updated_at` is updated (UTC).
- Mechanism:
  - Function `public.app_expire_ai_suggestions()` (PL/pgSQL) performs a single `update` (idempotent: repeated calls do not change the state after the first update).
  - Scheduled through the `pg_cron` extension: job `expire_ai_suggestions_hourly` runs every hour on the hour (`0 * * * *`).
- Security:
  - The function is `security definer` with an empty `search_path`; it uses the qualified name `public.ai_suggestions` and runs in the owner's context.
  - EXECUTE is revoked from `PUBLIC`, `anon`, and `authenticated`. The existing `pg_cron` schedule runs as `postgres` and retains access; trusted service-role permissions are unchanged.
- Operations:
  - The migration creates or resumes the schedule; an existing job with the same name is replaced (avoids duplicates).
  - Alternative when `pg_cron` is unavailable: a scheduled Supabase Edge Function calls a server endpoint that invokes the same logic.

---

## Initial Data (Seed)

- `training_types.code`: `easy`, `tempo`, `intervals`, `long_run`, `recovery`, `walk` (without `warmup`/`cooldown`).

---

## Extensibility (Beyond the MVP)

- Optional `profiles` table with additional user data.
- Partition `workouts` by `planned_date` for large volumes.
- More events in `ai_suggestion_events` (e.g., `generate`, `accept`).
- New goal types in `user_goals` (e.g., session count, time to goal, consistency).
- Integrations/imports (e.g., GPX/FIT) with `origin='import'` and a dedicated metrics source.
